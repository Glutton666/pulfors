# 고밀도 오프라인 카운트 자원 검증

## 조건과 결과

2026-10-05, Linux / Chromium **151.0.7922.34**, Expo 개발 서버의 실제 앱을
420×860 크기 iframe에서 실행했다. 실제 번들 한국어·영어 WAV를 디코딩하고
기존 PCM 렌더·출력 경로를 사용했다. 오디오 시계, 화면 표시 타이밍, 제스처,
앱 코드, 백엔드는 변경하지 않았고 배포하지 않았다.

- **240 BPM × 박마다 9분할**, 4박 문서: 논리적으로 초당 36개 기본 슬롯.
- Beat, Bar, 두 항목을 반복하는 Note 큐에서 동일한 리듬 사용.
- 기본 클릭은 classic, 추가 클릭은 한 개만 연결: tempo 또는 digital.
- 각 모드에서 영어+tempo / 한국어+tempo를 **각각 120초** 재생.
  이어 영어+digital / 한국어+digital / 영어+tempo / 한국어+tempo를 각각
  1.5초 재생. 모든 언어·추가음 교체는 정지한 상태에서 UI로 수행했다.
- 긴 재생 6회(명목상 합계 12분), 짧은 재생 12회, 정지·교체·재시작 18회.
  설정 조작, 준비, GC, 정지 뒤 관찰을 포함한 전체 테스트는 **약 15.2분**.
- 10초 간격 및 시작·정지·정지 1.6초 뒤에 측정: **144개 표본**.

**통과:** 출력 시작 112회 / 종료 112회, 동시 활성 출력 최대 **1개**,
최종 활성 출력 **0개**. 모든 정지 뒤 1.6초 관찰 구간에서 시작 횟수가
늘어나지 않았다. Note 큐는 다음 항목 준비 중 기존 출력을 멈추므로 짧은
준비 공백을 허용하되, 재생 복귀와 실제 큐 진행을 별도로 확인했다.

### 플레이어와 캐시

| 자원 | 재생 전 기준치 | 반복 재생·정지 결과 |
| --- | --- | --- |
| HTML 음원 플레이어 — Beat | 12개 | 매번 정지 후 12개 |
| HTML 음원 플레이어 — Bar | 45개 | 매번 정지 후 45개 |
| HTML 음원 플레이어 — Note | 12개 | 매번 정지 후 12개 |
| AudioContext | 각 모드 1개 | 전체 측정에서 1개 |
| 재생 중인 HTML 플레이어 | 0개 | 0개; 실제 출력은 PCM 루프 |
| Blob/WAV URL | 0개 | 0개 |
| 살아 있는 AudioBuffer | 모드 진입 직후 0개 | 재생 중 4개 / 정지 후 3개 |
| AudioBuffer 총 크기 | 최초 0바이트 | 재생 중 363,032 / 정지 후 10,224바이트 |
| 정규 PCM 캐시 | 최초 10개 / 205,308바이트 | 워밍업 후 16개 이내 / 최대 710,512바이트 |

Bar의 45개는 공통 클릭 풀 12개와 **기존 숨겨진 CustomSoundSetEditor의
미리듣기 플레이어 33개**다. 카운트 시작 전부터 존재한다.
재생 없이 Bar에 진입하는 별도 확인에서도 45개였고, Note로 떠나면 12개로
돌아왔다. 따라서 Beat의 기준치 12개를 Bar에 그대로 적용하지 않았다.
기존 초기 자원 사용량이며, 반복 카운트로 증가한 누수가 아니다.

AudioBuffer의 정지 후 3개는 기존 클릭 버퍼 캐시다. 각 모드의 첫 재생에서
만들어지며, 이후 정지마다 **동일한 10,224바이트**를 유지했다. 출력용
버퍼 한 개(352,808바이트)는 정지 후 사라졌다. 캐시의 정상 워밍업을
누수로 간주하거나 기존 풀·버퍼를 강제로 삭제하지 않았다.

### GC 후 메모리 추이

CDP로 GC를 실행한 뒤 측정했다. Heap은 React·Metro·화면 상태까지 포함하며,
`backingBytes`도 PCM만이 아니라 전체 V8 backing storage를 포함한다.
초기 개발 번들·캐시 워밍업과 모드별 UI 초기화 증가를 구분한다.

| 모드 | 정지 후 Heap 범위 (바이트) | 정지 후 backing storage 범위 (바이트) |
| --- | --- | --- |
| Beat | 32,631,360–33,224,132 | 15,162,793–15,280,505 |
| Bar | 33,979,088–34,645,556 | 15,163,554–15,281,266 |
| Note | 32,584,384–32,697,236 | 15,163,895–15,281,607 |

최초 Heap은 23,688,804바이트, backing storage는 14,742,050바이트였다.
최종 Heap은 32,697,236바이트, backing storage는 15,281,607바이트다.
초기 증가 이후 모드·캐시 상태에 따른 범위에서 유지됐으며, 반복마다
출력 버퍼·플레이어·WAV가 누적되는 현상은 관측되지 않았다.

회귀 테스트는 워밍업 이후 살아 있는 버퍼 수/크기와 backing storage,
Heap의 제한을 함께 검사한다. Heap은 개발 UI의 변동을 고려해 8 MiB,
backing storage는 1 MiB, AudioBuffer는 256 KiB의 여유를 둔다.
정규 PCM 캐시는 기존 한도인 16개 / 8 MiB를 항상 검사한다.

### 이전 언어·추가음 재사용 및 이중 출력

전체 출력 PCM의 16-bit 양자화 FNV-1a 지문을 비교했다.
네 조합의 지문이 서로 다르고, 같은 조합은 재시작·모드 전환·Note 큐
진행 후에도 같았다.

| 언어 / 추가음 | PCM 지문 |
| --- | --- |
| 영어 / tempo | 327462097 |
| 한국어 / tempo | 2373923874 |
| 영어 / digital | 1718244576 |
| 한국어 / digital | 1895083298 |

재생 중 별도 클릭 출력이 추가되지 않았고, Beat/Bar는 긴 재생 동안
처음 시작한 하나의 루프를 유지했다. Note는 항목 전환으로 출력을 다시
준비했지만 최대 동시 출력은 하나였다. 브라우저 오류는 0개였다.

## 네이티브 경로 자동 회귀

`tests/prerender-playback-reliability.test.ts`에 실제 준비·취소·출력 소유권
코드를 사용하는 두 테스트를 추가했다. 플레이어, WAV 저장·디코딩과 렌더
결과는 테스트 대역이므로 **실제 iPhone/Android 메모리 측정은 아니다**.

1. 고밀도 스케줄에서 언어·추가음을 교체하며 **120회 준비→재생→완전 정지**:
   - WAV 120개 생성 / 120개 해제, 동시에 소유한 WAV 최대 1개.
   - 렌더 플레이어 120개 생성 / 120개 해제, 최대 1개.
   - 매번 렌더 자원 기준치 0개로 복귀.
   - 중복 정지·discard 후에도 이중 해제가 없고 PCM 캐시 한도 유지.
2. WAV 준비 중 정지 후 늦은 완료 **24회**:
   - 각 WAV와 생성된 플레이어를 한 번씩 해제.
   - 이전 출력이 게시되지 않고 재생 호출 0회.

관련 Jest **5개 파일 / 101개 테스트**, 타입 검사 통과.
기존 `e2e/sound-extras.spec.ts`도 통과했다.
변경 파일 lint 오류는 없으며, 기존 테스트의 `require()` 사용 경고 1개는
남아 있다.

## 재현

설치된 Playwright Chromium과 **Expo 개발 서버**가 필요하다. 캐시 수치는
이미 초기화된 Metro 개발 모듈에서 읽으므로 production/`--no-dev` 서버로
대체하면 캐시 측정 조건 검사에서 명시적으로 실패한다.

```sh
# Replit에서는 기존 Start Frontend 워크플로를 사용한다.
# 별도 로컬 환경에서만 실행:
npx expo start --web --port 8081

COUNT_SOAK_SECONDS=120 npx playwright test e2e/count-audio-soak.spec.ts --reporter=list
npx playwright test e2e/sound-extras.spec.ts --reporter=list
npx jest tests/prerender-playback-reliability.test.ts tests/voice-count.test.ts \
  tests/pcm-preparation.test.ts tests/sound-overlays.test.ts \
  tests/voice-count-storage.test.ts --runInBand
npm run typecheck
```

짧은 동작 확인은 `COUNT_SOAK_SECONDS=2`로 가능하지만 장시간 검증의
대체가 아니다. 더 긴 관찰은 같은 변수로 각 긴 재생 구간을 늘린다.
브라우저 계측은 WeakRef를 사용해 측정 대상 버퍼·플레이어를 강하게
보관하지 않고, 측정마다 죽은 참조를 정리한다.

원시 표본은 [count-audio-soak-results.json](count-audio-soak-results.json)에
저장했다. 재실행 시 `COUNT_SOAK` 로그와 Playwright의
`count-audio-resource-samples` 첨부에 새 수치가 남는다.

## 확인 범위

이번 실행에서는 수정이 필요한 카운트 자원 누수나 정지 후 재생 문제를
발견하지 않아 앱 실행 코드를 변경하지 않았다.
실제 스피커·Bluetooth 출력, iOS/Android의 OS 메모리·네이티브 파일/플레이어,
잠금 화면·백그라운드 유지 음원은 이 브라우저 측정으로 보장하지 않는다.
네이티브 자원 소유권은 위 자동 회귀로 확인했으며, 실제 기기 측정은
별도 검증이 필요하다.
