# 첫 오디오 시작과 재생 UI 동기화 — 실기기 확인

**작성일**: 2026-09-12  
**대상**: 보급형 Android, 오래된 iPhone, 모바일 웹

## 확인 목적

오디오 준비가 늦어져도 첫 재생 요청이 수락되거나 첫 실시간 오디오 활동이 확인되기
전에는 화면이 재생 중으로 보이지 않아야 한다. 시작 실패나 활동 제한 시간 초과 시에는
엔진과 화면이 정지 상태로 돌아가고 다시 누르라는 안내가 표시되어야 한다.

기기 볼륨 0, 무음 모드, 고장 난 스피커, 잘못된 Bluetooth 출력 대상처럼 앱이 확인할
수 없는 물리 출력 문제는 이 검증의 실패로 보지 않는다.

## 공통 판정 기준

- 준비 중에는 spinner 또는 준비 상태가 유지된다.
- 준비 중에는 비트 강조, 진행 아크, 경과 시간, 재생 알림이 시작되지 않는다.
- 첫 소리 시작이 승인된 뒤에만 재생 버튼과 애니메이션이 재생 상태로 바뀐다.
- 실패하면 비트·타이머·엔진이 멈추고 “정지 후 다시 눌러보세요” 안내가 표시된다.
- 준비 중 취소하거나 다른 화면·모드로 이동한 뒤 늦은 오디오가 시작되지 않는다.
- PCM 워밍업은 출력 플레이어·볼륨·mute 상태를 만들거나 변경하지 않는다.
- 같은 URI의 반복 준비는 cache hit로 재사용되고, 오래된 URI·취소된 generation은 첫 박에 게시되지 않는다.

## Android

### 기본 Beat — 실시간 플레이어

1. 앱을 완전히 종료한 뒤 다시 연다.
2. 기본 사운드의 Beat 모드에서 재생을 누른다.
3. 첫 소리가 나기 전 화면 상태와 첫 소리 직후 화면 상태를 비교한다.
4. 30회 반복하고 빠르게 두 번 눌러 준비 중 취소도 10회 반복한다.

- [ ] 첫 오디오 활동 전까지 준비 상태가 유지됨
- [ ] 첫 오디오 활동 뒤에만 재생 UI와 알림이 시작됨
- [ ] 취소 직후 엔진이 멈추고 늦은 클릭이 이어지지 않음
- [ ] 재생을 다시 누르면 정상적으로 새 세션이 시작됨

### Bar 및 커스텀 사운드 — 렌더링 플레이어

1. 샘플이 있는 Bar 모드와 커스텀 사운드 Beat 모드를 각각 연다.
2. 앱을 재시작한 직후 첫 재생을 10회씩 확인한다.
3. 준비 중 모드를 바꾸거나 앱을 백그라운드로 보낸 뒤 복귀한다.

- [ ] 렌더링이 늦어져도 준비 표시만 보임
- [ ] 렌더링 플레이어의 시작 요청이 승인된 뒤에만 재생 중으로 바뀜
- [ ] 모드 변경·화면 이탈 후 이전 렌더링 결과가 재생되지 않음

## iPhone

1. 기본 Beat, Bar, 커스텀 사운드에서 앱 재시작 직후 첫 재생을 각각 10회 확인한다.
2. 저장 공간이 부족하거나 다른 앱을 많이 연 상태에서도 같은 절차를 반복한다.
3. 준비 중 홈 화면 이동, 화면 잠금, 전화·Siri 인터럽션을 각각 확인한다.

- [ ] decoder 준비가 늦어도 spinner와 정지된 비트 화면이 유지됨
- [ ] `play()` 시작 실패 시 재생 UI가 올라오지 않고 안내가 표시됨
- [ ] 인터럽션 뒤 자동 재개도 준비 → 시작 확인 → 재생 순서를 따름
- [ ] 준비 중 취소·이탈 후 오디오가 뒤늦게 시작되지 않음

## 모바일 웹

1. Safari와 Chrome에서 페이지를 새로 열고 첫 사용자 탭으로 재생한다.
2. 기본 Beat와 Bar 또는 커스텀 사운드를 각각 확인한다.
3. 브라우저의 자동재생 제한이 걸린 새 탭과 백그라운드 복귀 상황을 확인한다.

- [ ] AudioContext가 실행 상태가 아니면 재생 UI가 먼저 시작되지 않음
- [ ] 기본 Beat는 첫 Web Audio 활동 뒤에만 재생 상태로 바뀜
- [ ] 렌더링 루프는 실제 실행 상태가 확인된 뒤에만 재생 상태로 바뀜
- [ ] 시작 실패 시 정지 상태와 재시도 안내가 표시됨
- [ ] 새로 고른 음원으로 바꾼 직후 이전 URI의 늦은 PCM이 재생되지 않음
- [ ] 워밍업 취소 뒤 늦은 decode 완료가 click cache나 출력 source를 바꾸지 않음
