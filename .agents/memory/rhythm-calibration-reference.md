리듬 보정은 렌더 트랙의 소프트웨어 기준점과 탭의 단조 시계를 비교하는 개인 청각·입력 오프셋으로 취급한다. 화면 콜백마다 기준을 다시 찍지 않는다. 순수 하드웨어 지연이나 물리적인 DAC 출력 시각을 측정했다고 설명하지 않는다.

**Why:** 기준음 준비를 포함한 버튼 누름 시각은 탭과 비교할 기준이 아니며, 웹 AudioContext 실행과 네이티브 재생 수락도 실제 스피커 발음 시각을 보장하지 않는다. 물리 출력 측정 장치 없이 이를 하드웨어 지연으로 단정할 수 없다.

**How to apply:** 웹 출력 시계와 네이티브 플레이어 위치 관찰을 구분하고, 상태/브리지 지연은 미확인 오차로 남긴다. 출력 준비/재시작/실패와 누락·중복 박을 별도로 검증한다. 연습에서 입력 오프셋을 빼면 원본 기준 타격에도 같은 시간축 변환을 한 번 적용한다. 원본 타격 시각은 저장·원본 듣기를 위해 그대로 유지한다.

보정 탭은 누르는 순간을 직접 기록해야 한다. React Native Web의 기본 Pressable은 누름 활성화를 약 50ms 지연하며, `onPressIn`만 있는 버튼은 그보다 짧은 탭을 누락할 수 있다.

**Why:** 계산·훅 테스트는 통과했지만 실제 브라우저에서 기준음마다 빠르게 클릭하면 탭이 0개로 남아 보정이 실패했다. 느리게 누르는 테스트나 콜백 직접 호출은 이 문제를 발견하지 못한다.

**How to apply:** 타이밍 측정에 지연된 누름 활성화를 사용하지 않는다. 실제 출력 요청을 관찰하면서 짧은 down/up을 보내는 브라우저 검증을 포함한다. 잘못된 누름 수를 허용하도록 완료 기준을 완화해서 우회하지 않는다.

기준음 시작과 보정 탭 영역은 설정을 열었을 때 찾을 수 있어야 한다. 측정 중 사용자가 패드를 찾으려고 스크롤하게 만들지 않는다.

**Why:** 보정 계산과 자동 클릭 검사는 통과했지만 사용자는 “타이밍보정 탭하는 곳이 없어”라고 보고했다. 설정 하단의 패드를 자동으로 스크롤해 클릭하는 검사는 초기 가시성과 실제 사용성을 보장하지 않는다.

**How to apply:** 초기 화면에서 패드 전체가 설정창 안에 들어오는지 검사한다. 일반 세로 화면에서는 측정 영역을 고정하고 나머지 설정을 스크롤하며, 낮은 가로 화면은 보정을 맨 앞에 놓고 실제 스크롤 영역을 제한한다.

측정 중 포커스·키보드 이동은 수동 보정값 편집이나 측정 취소로 취급하지 않는다. 값이 실제로 달라졌을 때만 편집 경로를 실행한다.

**Why:** 보정값이 계속 0이라는 보고를 조사하면서, 변경하지 않은 숫자칸에서 포커스가 빠지는 것만으로 기준음 세션이 취소되는 경로를 브라우저에서 재현했다. 정상 터치만 반복하는 테스트로는 이 경로가 드러나지 않았다.

**How to apply:** 실제 터치 이벤트와 포커스 이동을 섞어 전체 측정을 검증한다. 알려진 양의 입력 지연을 준 검사는 결과가 단순히 0 이상이 아니라 양의 값으로 적용되는지도 확인한다.

네이티브 리듬 기준음 안정화에는 기존의 미리 렌더링한 클릭 트랙 재생을 사용한다. 웹의 미래 시각 예약만 적용하고 네이티브도 개선됐다고 보고하지 않는다.

**Why:** 사용자가 네이티브에서는 박 간격을 파일 안에 넣어 JS 부하와 분리해야 한다고 명시했다. 일정 오프셋 보정은 실행마다 달라지는 재생 시작 지연을 없애지 못하며, 클릭 간격과 녹음 0점은 별도 문제다.

**How to apply:** 반복 재생의 박 간격과 시작 요청·재생 수락·녹음 기준점의 관계를 분리해 검사한다. 실제 폰에서 확인하기 전에는 체감 개선을 확정하지 않는다. 기보 해석도 합성 입력 외에 실제 저장 연주와 독립적으로 확인한 정답 악보로 대조한다.
